# 常駐の資源（メモリ・GPU・CPU・ディスク）

常駐入力（[IME.md](IME.md)）の変換サーバとトレイアプリが、何にどれだけ資源を使っているかの実測。資源を減らす作業を始めるときに、測り直さずに済むように残す。速度の実測は IME.md「実測」と decisions.md D3〜D5・D12〜D17 にある。

## 測った機械と条件

- このデスクトップ: Core Ultra 5 245KF / RTX 5060 Ti 16 GB / RAM 32 GB、Windows 11。
- 変換サーバは torch（CUDA）・zenz-v3.1-small（fp32）・`CorePipeline` の既定（k=5、preselect、句読点 B、英字は打ったまま）。
- 日付は 2026-10-18。**ThinkPad（RAM 32 GB、内蔵 GPU のみで CPU で変換）では測っていない。**

## 常駐の全体（実際の常駐を外から測った値）

| プロセス | 再起動の直後（変換 2 件） | 約 25 時間動いた後（確定 414 件） |
|---|---|---|
| 変換サーバ（python.exe）作業セット / 専有 | 2.2 GB / 3.8 GB | 961 MB / 5.2 GB |
| 変換サーバ GPU 専用メモリ | 596 MB | 1,524 MB |
| トレイアプリ（RomajiSlmIme.exe）作業セット / 専有 | 55 MB / 37 MB | 34 MB / 47 MB |

- 待機中の CPU（10 秒間の平均）: 変換サーバ 0%、トレイアプリは 1 コアの 0.5%。25 時間の累計 CPU 時間は、サーバ 682 秒、トレイ 512 秒。
- 変換サーバは 2 つのプロセスに見える。venv の `pythonw.exe` はランチャー（2 MB）で、実体は uv の `python.exe`。
- **RAM を圧迫するかは専有（確保量）で見る。** 作業セットは、Windows が待機中に削ってページファイルへ追い出すので減って見える（25 時間後の 961 MB）。
- 外からの測り方（PowerShell）:
  - メモリ: `Get-Process -Id <pid>` の `WorkingSet64` と `PrivateMemorySize64`。
  - GPU（WDDM では `nvidia-smi` のプロセス別の値が N/A になる）: `(Get-Counter '\GPU Process Memory(*)\Dedicated Usage').CounterSamples` を `pid_<pid>_` で絞る。

## 内訳（読み込みの段階ごと）

`uv run python -m tools.memprof out.jsonl 600` の値（[tools/memprof.py](../tools/memprof.py)）。1 つのプロセスで順に読み込み、各段階の後に測った。

| 段階 | 作業セット | 専有 | 専有の増分 | GPU（確保 / 予約） |
|---|---|---|---|---|
| Python を起動 | 16 MB | 10 MB | — | — |
| `import torch` | 489 MB | 1,286 MB | **+1,276 MB** | — |
| `import core`（transformers を含む） | 495 MB | 1,291 MB | +5 MB | — |
| 読み段の初回（読みの LM・英単語・編集と語の索引） | 808 MB | 1,605 MB | +314 MB | — |
| Mozc の辞書（marisa-trie の索引） | 823 MB | 1,619 MB | +14 MB | — |
| CUDA の文脈 | 955 MB | 1,923 MB | +304 MB | 0 / 2 MB |
| `CorePipeline`（zenz の重み 90.45M パラメータを GPU へ） | 1,437 MB | 2,913 MB | +990 MB | 345 / 400 MB |
| 変換 75 件の後 | 1,919 MB | 4,251 MB | **+1,338 MB** | 355 / 678 MB |

- 最大は `import torch` の 1.3 GB。torch 本体と CUDA のライブラリの分で、変換の中身とは関係がない。
- zenz の重みは fp32 で 345 MB（90.45M × 4 バイト）。GPU の確保量はほぼこれだけ。
- 最初の変換で専有が大きく増える。8 件で試すと、1 件目だけで 2,907 → 3,838 MB（+931 MB）、8 件で 4,084 MB だった。原因は切り分けていない。候補は、CUDA のカーネルの遅延読み込み、cuBLAS の作業領域、transformers の生成の初回の確保。GPU の予約も同時に 400 → 678 MB に増える。
- 読み段の部品の大きさは READING.md にもある（読みの LM＋英単語＋語の索引の最大 RSS 307 → 361 MB）。辞書は KANAKANJI.md（marisa-trie で読み込み後 +17 MB）。

## 使っているうちに増える分

同じ計測の続き。入力は eval/sets の romaji（synth_user から順に）。

| 変換の件数 | 専有 | `_lm_step` の項目数 | `_lm_end` | `_parses_as_romaji` | GPU（確保 / 予約） |
|---|---|---|---|---|---|
| 75 | 4,251 MB | 276,155 | 12,921 | 1,202 | 355 / 678 MB |
| 150 | 4,362 MB | 496,022 | 21,279 | 1,565 | 355 / 678 MB |
| 300 | 4,525 MB | 881,346 | 32,778 | 1,917 | 355 / 678 MB |
| 450 | 4,651 MB | 1,183,911 | 40,799 | 2,142 | 355 / 678 MB |
| 600 | 4,799 MB | 1,512,493 | 47,946 | 2,316 | 355 / 678 MB |
| キャッシュを消した後 | 4,717 MB | 0 | 0 | 0 | — |
| `torch.cuda.empty_cache` の後 | 4,685 MB | — | — | — | 355 / 402 MB |

- 75 件目からは、1 件あたり約 1 MB ずつ専有が増え続ける（75 → 600 件で +548 MB）。
- **`core/reading.py` の `_lm_step`（`lru_cache(maxsize=None)`）が、1 件あたり約 2,500 項目ずつ増え、600 件で 151 万項目になっても頭打ちにならない。** 項目は（直前のかな, 弧のかな）の組なので、新しい文を打つたびに増える。増える分の大半はこれとみられる（項目の大きさから見積もったのではなく、増え方が揃っていることからの推測）。
- **キャッシュを後から消しても、専有は 82 MB しか戻らない。** Python は解放したメモリをプロセスの中に持ち続け、OS に返さない（細切れの小さいオブジェクトのため）。減らすには、消すのではなく最初から上限を付ける必要がある。
- GPU の確保量は 355 MB で増えない。予約は最初の変換で 678 MB になり、600 件の間は増えなかった。`empty_cache` で 402 MB に戻る。
- 実際の常駐では、GPU が 25 時間で 596 → 1,524 MB に増えていた。この計測（左文脈なし、600 件）では再現しなかったので、原因は分かっていない。左文脈つきの長い入力で一時的に大きく確保した分を、torch のキャッシュが持ち続けている可能性がある（未確認）。

## 起動の時間

`server.log` の「ready in」は、2026-10-16〜18 の 25 回で 4.7〜67.2 秒（中央値 6.7 秒）。30 秒を超えたのは 6 回（30.7・31.8・31.9・32.3・58.9・67.2 秒）。67.2 秒は 2026-10-18 02:02 の更新の直後で、そのとき別のプロセスが GPU に 10.6 GB を持っていた。遅い回の原因は確かめていない。

## ディスク

- `%LOCALAPPDATA%\romaji-slm` は `du` で 4.5 GB。`app` と `app.prev`（自動更新が残す一つ前の版。IME.md「入れる・外す・更新する」）の両方に `.venv` がある。torch は uv のキャッシュから hardlink されるので、`du` の値は実際に増えたディスクより大きい。
- zenz-v3.1-small の Hugging Face のキャッシュは 173 MB。

## 減らす手の実測（2026-10-21、コードは変えていない）

本人の依頼「精度と速度を大きく落とさずに RAM, VRAM, CPU, GPU の使用率を下げることができる方法を検討して報告して」で測った。判断の整理は decisions.md D49。

### 結論（推奨の順）

出力を変えない手（1〜4 は重ねて全セット 2400 文で、5 は 150 要求で、出力が同じことを確かめた。下の「全セットの出力」）:

1. **ONNX 版（GPU の無い機械）で torch を読まない。** transformers 5 の `AutoTokenizer` は `transformers.generation` を通して torch を import する。
   ime/server.py の `pick_device("auto")` も GPU の有無を見るために torch を読む。
   トークナイザを tokenizers（Rust）で `vocab.json`・`merges.txt` から組むと、評価セットのプロンプトと正解 6,808 文で同じ id を返す。
   語彙 6,000 個のトークン・EOS・PAD も同じ。専有は −950 MB、作業セットは −550 MB。待ちは同じだった。
   GPU の有無は torch 以外で見る必要がある。初回の ONNX の書き出しには torch が要る。
2. **ONNX Runtime のスピン待ちを止める**（`session.intra_op.allow_spinning=0`）。応答のあと 0.3 秒ほど約 3 コアが空回りしていたのが消える。
   1 要求あたりの CPU 時間は、空回りを含めると 3,212 → 1,839 ms（−43%）、計算中だけなら 2,379 → 1,838 ms（−23%）。待ちは同じだった。
3. **読み段の 3 つのキャッシュに上限を付ける。** 上限が無いのは `core/reading.py` の `_lm_step`・`_lm_end` と `core/kana_lm.py` の `KanaLM._memo`。
   長く使ったときの増え方がほぼ止まる（2,000 文で +1.6 GB → +0.07 GB）。読み段の 1 回は +6 ms（+21%）で、要求全体では振れ（±5%）と区別できない。
   試した上限の値（20 万・2 万・30 万）は試した値で、詰めた値ではない。
4. **要求のあと、暇なうちに ONNX Runtime のアリーナを縮める**（小さい 1 回の実行に `memory.enable_memory_arena_shrinkage=cpu:0` を付ける）。
   150 要求後の専有は −460 MB、作業セットは −300 MB。縮める処理を応答の前に入れた測り方で、別の書き方は +13 ms だった。
   応答を返したあとに縮めれば待ちに入らない見込みだが、確かめていない。
5. **GPU の機械では、暇なうちに `torch.cuda.empty_cache()`**。GPU 専用メモリは 1,346 → 556 MB、専有は −480 MB で、速さは同じだった。
   使っていない予約を返すだけで、変換中に要る量は減らない。

1〜4 を重ねると（今の版と交互に 2 回ずつ）:
- 150 要求後の専有は 2,823 → 1,404 MB（−50%）、作業セットは 1,900 → 1,033 MB（−46%）。
- CPU 時間は、空回りを含めて 3,099 → 2,050 ms（−34%）。
- 待ちは 1 位まで 452 → 487 ms（+8%）、別の書き方 180 → 204 ms（+13%）。このとき機械は負荷が高く、同じ条件の 2 回で ±5% 振れた。

本人の判断が要る手（出力か振る舞いが変わる）:

6. **torch 版の重みを fp16 にする**（`model.half()`。logits は `.float()` してから log_softmax）。全セットで 5 文の出力が変わる。
   壊した文は exact・loose とも 0 件で、loose では 2 件直した。D16 の「出力が同じ」は満たさない。
   torch の確保は 355 → 193 MB、別の書き方は 44 → 20 ms、GPU 全体の平均電力は 33 → 25 W。
7. **暇なときに別の書き方を揃えるのをやめ、候補ウィンドウを開いたときだけにする**（D47 の「開いたときか暇なときに」の片方）。
   1 要求の計算の約 3 割（CPU 時間 1,839 ms のうち 510 ms）が別の書き方で、その分の CPU・GPU の仕事が減る。
   代わりに、開いたときの待ちが CPU で約 170 ms、GPU で約 44 ms 増える。
   利用履歴（2026-10-20 以降の確定 210 件）で 1 位以外を選んだのは 3 件。ウィンドウを開いた回数は記録していない。
8. **トレイアプリのタイマーを、未確定の文も待っている要求も無いあいだは間隔を広げる。** 今は 50 ms ごとに起きていて、待機中も 1 コアの 0.26% を使う。
   このデスクトップの 29 時間で、トレイ 361 秒・変換サーバ 170 秒（torch＋GPU）。ノート PC では、起きる回数が省電力を妨げる。
   広げると、修飾キーの取りこぼしを直す処理（`ResyncModifiers`）が遅れる。測っていない。

採らない手:
- **ONNX 版の重み 8 ビット（MatMulNBits）。** 全セットで 37 文が変わり、壊したのは exact で 4・loose で 8、直したのは 6・7。
  利点は専有 −200 MB・CPU 時間 −20%・1 位まで −6〜11% で、速さの差は振れと同じくらい。
  llama 版の Q8_0 も同じ傾向で正常な入力を壊した（LLAMA_PARITY.md）。
- **int8 動的・4 ビット**: 150 要求で 1 位が 41 件・16 件変わり、13 件・3 件壊した。
- **アリーナを切る**: 待ちが +37%。**アリーナを要るだけ伸ばす**（kSameAsRequested）: かえって増えた。
- **スレッドを減らす**: 待ちが 1.4 倍（2 本）・2.3 倍（1 本）。スレッド数は本人の決定で 4（D42）。
- **GPU の機械で torch をやめ、ONNX Runtime の DirectML 版にする**: torch の分のメモリは減る（専有 1.6〜1.7 GB）が、生成の 1 手が torch の 6 倍（下の表）。
  手ごとに KV の長さが変わる今の作りが DirectML に合わない。KV を GPU に固定長で置く作りに変えれば違う可能性はあるが、試していない。
- **デスクトップを CPU（ONNX 版）にする**: 待ちが約 2.3 倍（198 → 452 ms）。
- **xsmall（22.5M）にする**: 精度が下がる（D5: AJIMEE 84.5% → 70.0%、誤補正が 2 倍）。
- 読みの LM を 5-gram にする案は、常駐メモリが 307 → 705 MB になるので採らなかった（READING.md）。

**ThinkPad では測っていない。** メモリの減り方は機械によらない見込みだが、待ちと CPU 時間は ThinkPad で確かめる必要がある（ThinkPad の測定は本人の決定で最後に行う。D41 の回答）。

### 測った機械と条件

- このデスクトップ（Core Ultra 5 245KF / RTX 5060 Ti / RAM 32 GB）。ほかのセッションが同時に CPU を使っていて、同じ条件を 2 回流すと平均で最大 20% 違った。
  比べるものは続けて、なるべく交互に流した。
- 要求の流れは常駐と同じ: `ime.server.Lists` の first（1 位と読みの候補）、次に full（暇なときに揃える別の書き方）、間を 300 ms 空ける。

- ONNX 版は ONNX Runtime 1.31 の CPU、スレッド 4、句読点は常駐と同じ既定（D48）。

### 作り方（再現のため。コードはリポジトリに入れていない）

- **torch を読まないトークナイザ**: `tokenizers.Tokenizer(models.BPE.from_file(vocab, merges))` に、`pre_tokenizers.ByteLevel(add_prefix_space=False)` と `decoders.ByteLevel()` を付ける。
  `sys.modules["transformers"]` を差し替えて `OrtBackend` に渡した。
- **アリーナを縮める**: `RunOptions.add_run_config_entry("memory.enable_memory_arena_shrinkage", "cpu:0")` を付けて、1 トークン・KV 空の実行を 1 回する。
- **量子化**:
  - 8・4 ビットは `onnxruntime.quantization.matmul_nbits_quantizer.MatMulNBitsQuantizer(bits=8|4, block_size=32, is_symmetric=True, accuracy_level=4)`。onnx-ir が要るので `uv run --with onnx-ir` で動かした。
  - int8 動的は `quantize_dynamic(op_types_to_quantize=["MatMul"], per_channel=True, extra_options={"MatMulConstBOnly": True, "DefaultTensorType": FLOAT})`。
  - 量子化したのは 37 個の MatMul（注意の出力の Gemm 12 個は対象外）。
- **全セットの比較**: ONNX は `core.ort_backend.default_path` を差し替えて `eval.parity run` を回した。fp16 は `ZenzScorer` の読み込みのあとに `model.half()`。
- **DirectML**: プロジェクトの環境は変えず、`uv run --no-sync --with onnxruntime-directml==1.24.4` で動かした。
