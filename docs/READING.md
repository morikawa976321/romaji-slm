# 読みラティス（工程2: 打鍵列 → 読みの N-best）

[REDESIGN.md](REDESIGN.md)「推奨構成」の最初の段。`core/reading.py` の `readings(keys, n=20, max_edits=2)` が、打鍵列から読みの候補（`core/types.py` の `Reading`）を返す。英語か日本語かはここで決めず、両方を N-best に残す（決めるのは後段）。後段は上位5件だけを比べる（`core/pipeline.py` の k）ので、上位5件は「直さない／直す／英字のまま読む」の違う仮説を広く拾うように選ぶ（下の「上位5件の選び方」）。

```
uv run python -m core.reading "githubnipushshiteoite"      # N-best とコストの内訳
uv run python -m eval.reading_bench --fails 10             # 合格条件の測定（AJIMEE・user_style・raw_tokens）
uv run python -m eval.reading_bench --set wac-test         # コスト調整に使った別セット
uv run python -m eval.reading_bench --preselect            # 上位5件を辞書の変換コストで選び直して測る（core/preselect.py。要 core.fetch_mozc）
uv run pytest tests/test_core_reading.py
```

初回は言語モデルの素材（Mozc 辞書 約60MB、Wikipedia 注釈コーパス 3779 文書）を github から取り、`models/reading/kana_lm.pkl`（約30MB）と `models/reading/mozc_readings.marisa`（Mozc の読み→最小コストの索引、約5MB）を作る（30秒〜2分）。`models/` はコミットしない。`uv run python -m core.kana_lm build` で両方を作り直せる。`kana_lm.pkl` は中身の版（`core/kana_lm.py` の `VERSION`）が違えば読み込み時に作り直す。`mozc_readings.marisa` も Mozc の辞書テキストも無い環境では、語のコストを使わずに動く（変換の途中で辞書を取りに行かない）。

## 仕組み

打鍵列の各文字位置を節点にし、次の弧を張る。弧は「打鍵列の区間 [start, end) → 読みの断片」で、コストを持つ。

| 弧 | 内容 | コスト |
|---|---|---|
| 正規ローマ字 | `core/romaji_table.py`（Microsoft IME / Google 日本語入力と同じ表。`eval/romaji_kana.py` から移した）。si/shi, ti/chi, tu/tsu, hu/fu, zi/ji, sya/sha, tya/cha/cya, ja/jya/zya、x/l の小書き、fa・thi・dhi・twu・wi・va などの外来音。`nn`→ン、`n`（母音・y・n の前以外）→ン、`n'`→ン、子音の重ね・`tch`→ッ、`-`→ー | 0 |
| nn の揺れ | `nn`+母音・y を「ン+な行」とも読む（`jikkennokekka`→ジッケンノケッカ） | 3.0 |
| ti/di の揺れ | `ti`→ティ、`di`→ディ（user_style に `yu-zabiriti-` の打ち方がある） | 2.0 |
| 編集 | 音節表の各綴り（＋単独の n・nn。x・l で始まる小書きと q で始まる綴りは直し先にしない）に1編集を施した綴り→元の音節。置換は QWERTY 隣接キー（`core/keyboard.py`、`data/noise.py` と共有）、脱字（1字補う）、余計な1字（重ね打ちか隣接キー）、隣接2字の入れ替え。ほかに、促音の子音を落とした形（kite→キッテ）、音節の後ろの i・u・n を落とした形（tasou→タイソウ）、音節をまたぐ入れ替え（ornipikku→オリンピック）、促音の子音が隣のキーに化けた形（tsuku6ta→ツクッタ）、促音の前の余計な1字（iesshin→イッシン） | 置換 3.0・脱字 3.5・余計な1字 3.0（重ね打ち 2.5）・入れ替え 3.0 |
| 辞書の語 | Mozc の頻出語（かな4字以上・生起コスト 4000 未満、約1.5万語）の綴り（ヘボン式。ン は母音・y・n の前で nn）に、編集1〜2つ（入れ替えは1つに数える）で一致する区間 → 語のかな1本の弧。編集1つの弧は、正規ローマ字の弧だけで読める位置（音節の切れ目）から張る。編集2つの弧は、正規ローマ字の弧だけでは読み切れない英字の連続の、読めなくなる位置の 12 字手前から張る（1つの音節に打鍵ミスが2つある語: `kaggnaekata`→カンガエカタ）。候補は綴りの先頭7字の対称削除の索引（SymSpell）で引き、帯状の DP で確かめる | 編集のコストの和 ＋ 2.0（探索では `SEARCH_EDIT` の和 ＋ 1.0） |
| 英語 | 打鍵列の部分文字列が英単語リストに一致する区間（`kind="en"`、`surfaces` は登録表記→綴り）。1編集で一致する区間も（`githib`→github）。英字と `.` `-` 数字の塊（llama.cpp、claude.md、gpt-2、v3.1）も1区間にできる | 下記 |
| 辞書に無い英数字列 | かなの弧が1本も出ない英字（`jr` の j・r、`cdma` の c・d）か、すぐ後ろに数字が続く英字の連続（`int8` の int）を含む、10字までの英数字列（`kind="en"`、`surfaces` は綴りだけ）。読めない字・数字にはさまれた助詞の綴り（`sram\|to\|dram`、`bf16\|to\|fp16`）はまたがない | 2.0 ＋ 読めない字・数字の直前の字 0.15/字 ＋ かなに読める字 1.0/字 |
| 辞書に無い英字列（最後の逃げ道） | 3字までと、英字の連続の終わりまで | 5.0 + 1.0/字 |
| 数字 | 数字の連続（中の `.` `,` を含む: 3.14） | 0（英字に挟まれると 1.5、母音・n 以外の英字の直後なら 2.5） |
| 記号 | `,`→(、 ,) `.`→(。 .) `?`→(？ ?) `!`→(！ !) `[`→(「 [) `]`→(」 ]) `/`→(・ /) `:`→(： :) など。数字・英語の塊の中の `.` は持たない。`-` は記号としても読む（母音の直後は長音がふつうなので高め: `cve-2024`） | 0（`-` は 1.0、母音の直後の `-` は 3.0） |

**大文字の区間**: 大文字で始まり、大文字・数字と、大文字・数字にはさまれた `.` `-` が続く範囲（`GUI`、`GPT-4`、`A100`）は、打ったままの英語区間1本だけにする（コスト 0、内訳 `verbatim`。綴りも大文字のまま zenz に見せる）。その間の小文字の部分は、それぞれを独立した打鍵列として上の弧を張り、位置をずらして戻す。区間をまたぐ弧は無く、区間の手前の `n` は終わりの `n` として「ン」になる（`honUI` → ホンUI）。小文字だけの打鍵列は従来と同じ弧になる（本人の決定 2026-10-18、decisions.md D34）。

制約: 1弧に編集は1つまで（＝1音節・1英単語に1編集まで。辞書の語の弧だけ2つまで）、1文で `max_edits` まで（辞書の語の弧の2編集も2つに数える）。無修正の経路は常に残る（辞書に無い英字列の弧があるので、どんな打鍵列にも編集0の経路がある）。

さらに、かなの弧には**読みらしさ**を足す: カタカナの文字 4-gram（`core/kana_lm.py`）で `0.3 × Σ(min(−log P(字|直前3字), 9) − 3.5)`。記号の後と文頭は文脈を文頭（`^^^`）に、**英字の区間の後は「英字の語の直後」（`^^@`）、数字の後は「数字の直後」（`^^#`）**の文脈にする（下の「英字・数字の直後の文脈」）。辞書に無い英数字列の弧の直前でかなの連続が終わるところには、`0.3 × (min(−log P(終わり|直前3字), 9) − 1.5)` を足す（`オ|cr`、`ギ|thib` のような切れ目は高い）。

探索: 状態を（位置, 使った編集の数, 直前3字のかな）にして前向きに最良コストを求め、入ってくる遷移を覚えておき、後ろ向きに最良優先で経路を取り出す。各位置で、全体の上位16状態と編集数ごとの上位4状態だけを広げ、到達先の位置の最良より 10 以上悪い遷移は記録しない。**探索では編集を安く数える**（置換・脱字・余計な1字 2.0、重ね打ち・入れ替え 1.5。`SEARCH_EDIT`）。返す `Reading.cost` は上の表のコストのまま（同じ区間列が編集を使う経路と使わない経路の両方で作れるとき、例えばジッケンノケッカの脱字 n と nn の揺れは、安いほうのコストと内訳を返す）。

探索の間は Python の GC を止める（`readings()`）。探索は1回で数十万個のタプル・リストを作り、その間に世代別 GC が何度も走って全部を走査していた（AJIMEE 20〜39字の p95 が GC ありで約280ms、なしで約40ms）。作るものは循環参照を持たず、戻るときに参照カウントで解放される。

`Reading.breakdown` の内訳: `edit`（編集。辞書の語の弧の 2.0 を含む）、`en`（英語区間の固定分＋頻度）、`en_romaji`、`en_cut`、`nn`、`loan`、`raw`（辞書に無い英数字列）、`num_in_word`、`num_cut`、`sym`、`verbatim`（大文字の区間。0）、`lm`（読みらしさと、英字列の前のかなの終わり。負にもなる）。合計が `Reading.cost`。

### 上位5件の選び方（`_select`）

探索のコスト順に n + 20 件を取り出し（取り出し中の探索のコストが元のコストの最小を超えるまでは続ける）、そこから選ぶ。

1. **1位は元のコスト（`Reading.cost`）の最小。** 探索で編集を安く数えても、きれいな入力の1位と誤補正は変わらない。
2. **2〜5位は、探索のコスト ＋ 0.0001 ×（語のコスト − 1位の語のコスト）− 0.5 × 読みらしさ − 0.5 × 編集数 の小さい順。** 語のコストは、かなの連続を Mozc の語（読み→最小の生起コスト）に分けたときの最小で、語1つごとに 6000 を足す（接続コストの代わり。`core/kana_lm.py` の `WordCost`）。文字 4-gram では区別できない「別の正しいかなになった打鍵ミス」を、語の知識で拾う（`ヨッキュノ` と `ヨッキュウノ`、`ウラッテイタ` と `ウタッテイタ`）。
3. 辞書に無い英数字列を含む候補は5件のうち2件まで（打鍵ミスでできた子音の並びを英字のまま残す変種が枠を埋めないように）。
4. 「直さない」（編集0）と「英字のまま読む」（辞書に無い英数字列を含む）候補が1件も入らなければ、後ろの枠をそれぞれのコスト最小のものに入れ替える。
5. 上位5件とその後ろは、それぞれ元のコスト順に並べる（返す列は全体ではコスト順にならない。1位は必ずコスト最小）。

## コストの決め方と根拠

### 読みらしさ（文字 4-gram）が要る理由

打鍵ミスの約半分は別の正しいローマ字になる（AJIMEE に `data/noise.py` で1〜2個入れた200件のうち94件は、編集なしでかなに読み切れる。例: `noiraigakuruyouni`→`noiraiakuuyouni`＝ノイライアクウヨウニ）。編集コストだけでは、こうした入力は必ず「編集なしの誤読」が1位になり、正解は1編集の経路の山（1文で数十〜数百本、どれも同じコスト）に埋もれる。最初の実装（読みらしさなし）は打鍵ミス入りの上位5が 24.5%（49/200）だった。

### 言語モデルの素材

- **Mozc dictionary_oss の読み**だけで作った 3-gram: AJIMEE の読みで 1字あたり 3.85 nats。語単位なので、助詞の続き方など語をまたぐ連鎖が無い。打鍵ミス入りの上位5は 48%（96/200）。
- **京都大学 Wikipedia 注釈コーパス**（人手の読み付き、train+dev 34,142 区間・約49万字）を足すと 3.22 nats、Mozc の重みは α=0, 0.3, 1, 3 のうち `data/fixtures/zenz_like.jsonl` で最良の α=3 を採った。
- 次数: 3-gram→4-gram で WAC test の打鍵ミス入り上位5が 143→154/200、1位が 63→92/200。5-gram は下の「効かなかった案」。
- 文コーパスの候補のうち、Tatoeba・Wikipedia ダンプ・青空文庫はこの環境から届かなかった。京都大学ウェブ文書リードコーパス（KWDLC）は届くが、本文の著作権者の許諾を得ていない旨が README にありライセンスの明記が無いので使っていない。

### 英字・数字の直後の文脈

以前は英字・数字の区間の後を文頭に戻していた。文頭の −log P は ノ 3.89・ヲ 5.64 で、`jr|ノ`、`cdma|ノ` のように英字の後に助詞が来る読みが損をし、英字列が後ろの助詞まで飲み込んだ（`kddiノ` より `kdd|イノ`）。Wikipedia 注釈コーパスの、英字の語（約2800）とカタカナ表記の名詞の直後に続くかなの連続を「英字の語の直後」の印 `@` 付きで、数字の語の直後を印 `#` 付きで数えた（`core/kana_lm.py` の `wac_after_runs`。英字の語だけでは少ないので、文中で同じように助詞・する が続くカタカナ語で補う。連続は次の英字・数字・カタカナ名詞の手前で切る）。印を含む履歴の n-gram だけを足すので、印の無い文脈の確率は変わらない。`@` の後の −log P は ノ 1.84・ヲ 3.29・ハ 2.42。

### 重みと編集コスト（調整は AJIMEE ではなく WAC test で）

調整用に、Wikipedia 注釈コーパスの **test**（言語モデルの学習に使っていない）から、かなと句読点だけの 10〜45字の文を200件取り（`eval/reading_bench.py --set wac-test`）、同じ手順で打鍵ミスを入れた。AJIMEE は最後の測定にだけ使った。

| 0.2 | 3.0 | 200 | 0 | 115 |
| 0.3 | 3.0 | 200 | 0 | 127 |

`data/noise.py` の打鍵ミスは、1か所あたり置換 35%（隣接キー 5〜6 通りに分かれる）・脱字 25%・余計な1字 20%（半分は重ね打ち）・入れ替え 20%（1通り）なので、1通りあたりでは入れ替え・重ね打ち・脱字が置換より起こりやすい。表の最良はこれと同じ向き。

語のコストの重みと形（2〜5位の点数）は、WAC test の候補（各文 40〜60 件）を書き出して机上で格子探索した。語1つに足す定数 1000・2500・4000・6000・9000 のうち 6000、語のコストの重み 0.00005〜0.0003 のうち 0.0001、読みらしさ・編集数の係数 −1.0〜+1.0 のうち −0.5・−0.5 が WAC test で最良（上位5 172/200。語のコストなしは 157）。

その他の値:
- `lm_base` 3.5: かなの1字あたりの平均的な −log P。これを引くので、英語区間がかなを置き換えても読みらしさの合計が系統的に得も損もしない（引かないと、かなを減らす英語区間が常に得をする）。3.0 と 3.5 で結果はほぼ同じ。
- `lm_eos_base` 1.5: かなの連続の終わりの −log P の平均（Wikipedia 注釈コーパスの連続 2万個で 1.42）。辞書に無い英数字列の前の終わりだけに掛ける（AJIMEE の打鍵ミス上位5 +1）。辞書の英単語・数字の前にも掛けると +3 だったが、`githibnipush…`（github の打ち間違い）の1位が「ギティンニpush…」に変わった（「英字の語の直後＋ニ」で連続が終わる例が学習データに少ない）。
- `lm_cap` 9: これが無いと `lyu`（ュ）・`syi`（シィ）のような珍しいかな1字が、隣接キーの置換（キュ、ショ）に負けた。
- 英語区間: 固定 2.0（技術語 1.5）＋ 0.3×(6.5−zipf)（技術語は 0.3 まで）。綴りがそのままローマ字として読める語（kai、mono、issue）は +1.0（技術語 +0.5）。子音で終わる英語区間の直後に母音・y が来る形（sum|ou、rag|iri）は +2.5。これらが無いと、AJIMEE のきれいな入力で sumou→sum+オウ、uragiri→ウ+rag+イリ のように一般語が割り込んだ（192/200）。
- 辞書に無い英数字列: 読めない字 0.3/字（区間 2.0）で raw_tokens の上位5 33/39（AJIMEE の打鍵ミス上位5 150・1位 58）、0.15 で 35/39（149・55）、0 で 35/39（148・53）。0.15 にした。区間の固定分を 2.5 にすると 32/39。読める字の 1.0 は最後の逃げ道（`raw_char`）と同じ。
- nn の揺れ 3.0: 1.5 だと読みらしさが「ン+な行」を好み、`kinnitsuna`（キンイツナ）がキンニツナになった。
- 状態数の上限: 12/3（全体/編集数ごと）→16/4→24/6 で AJIMEE の打鍵ミス上位5 147→150→151、20〜39字の所要の中央 26→28→35ms（語のコストを入れた後に測った）。速度の条件（変更前より2割以上遅くしない）に収まる 16/4 にした。
- 音節の後ろに補う脱字は i・u・n だけ（a・e・o を足しても WAC test の上位5は同じで、弧が増えて遅い）。

## 実測（2026-10-14）

条件: クラウドのコンテナ（Intel Xeon @ 2.10GHz、4 vCPU）、Python 3.13、1プロセス。所要は `readings()` 1回（n=20）の時間で、言語モデルの読み込みを除く（常駐を想定し、読みらしさのメモは件をまたいで共有）。変更前は分岐元（df697ee）のコードと言語モデルを同じ機械で測り直した値（AJIMEE の打鍵ミス上位5は 2026-10-12 の記録 127 に対し 126）。**ThinkPad（Core Ultra 7 255H）では測っていない。**

## 難しい打鍵ミス（typo_hard、2026-10-15）

失敗の内訳（AJIMEE の打鍵ミス入り、変更後、N=100 で取り直して数えた）: 上位5 149件、6〜20位 10件、21〜100位 5件、100位以内に無い 36件。100位以内に無いもののうち、経路そのものが無いのは、1音節に2つの打鍵ミス（`ukagaeei`＝ウカガエル、`sjani`＝サイニ）と、単独の n の制約（#7）。残りは経路はあるが、文字 4-gram の読みらしさで正しい読みより良く見える読みが多い。

## 未解決の論点

1. **打鍵ミスの上位5 80% に届かない（AJIMEE 74.0%、WAC test 86.5%）。** → 2026-10-15、下の案を `core/preselect.py` に関数として置いた。読み段＋preselect で AJIMEE 160/200（80.0%）・WAC test 177/200、20〜39字で1文 約 +72ms（上の「難しい打鍵ミス」）。後段への組み込みは未着手。以下は 2026-10-14 時点の記述。 品詞の接続コストまで使う辞書の Viterbi（`core/kanakanji.py` の `convert`）で2〜5位を選ぶと、机上で AJIMEE 164/200（82%）・WAC test 181/200 になった（読み段の候補 40 件のうち、1位以外を「探索のコスト ＋ 0.0003 × 変換のコスト差 − 0.5 × 読みらしさ − 0.5 × 編集数」で並べ替え）。ただし `convert` は1回 1〜3.5ms（10〜24字）で、40件に掛けると読み段の所要が数倍になる（語のコストで絞った上位8件だけでも AJIMEE 160/200 だが +15〜25ms）。読み段の所要の条件の中では入らないので、後段（工程3）で「読み段の候補 20〜40 件 → 辞書の変換コストで5件に絞る → zenz」とする案を提案する。後段はもともと各読みを辞書ラティスに通しているので、読み1つあたり変換1回分の追加で済む。
2. **きれいな入力の 1位 100% と、打鍵ミスの復元はトレードオフ。** 1位は元のコストで決め、2〜5位だけを打鍵ミス寄りに選ぶことで、きれいな入力の1位と誤補正を変えずに上位5を上げた。1位そのもの（AJIMEE の打鍵ミス入りで 27%）は上がっていない。
3. **速度。** 20〜39字は中央 29ms・p95 51ms（変更前 29ms・212ms）。60字を超えると中央 120ms・p95 230ms。ほぼすべて Python の遷移ループ（状態×弧）。ThinkPad 未計測。速くするなら、脱字の弧（母音1字 → カ・サ・タ…の約20通り）を減らすか、探索部分を Rust/C に移す。
4. **返すコストの尺度。** 弧のコストは変えていない（新しい弧の追加と、英字・数字の後のかなの読みらしさ、英字列の前のかなの終わりの読みらしさ）。AJIMEE で、きれいな入力の1位のコストの分布は変更前と同じ（平均 −3.22、中央 −2.06、p10 −9.32、p90 1.94）。打鍵ミス入りの上位5のコストは中央 1.64→2.01・p90 6.29→6.74（編集2つの候補が上位5に増えた分）。上位5に入った正解のコストは中央 1.08→1.19、うち編集2つの正解は 38→53件・中央 1.13→2.22。1位との差は中央 0.13→0.48。後段の w=4 では、新しく拾った編集2つの正解は `−4 × 2.2` 前後の不利を zenz の尤度で取り返す必要がある。英語を含む user_style（tech）の1位のコストは平均 2.69→2.53（英字の後の文脈）、raw_tokens の正解のコストは中央 7.27→3.54（辞書に無い英数字列の弧）。
5. **評価の正解の付け方。** AJIMEE の正解読みは表記の揺れを含む（スラブ／スラヴ）。`eval/reading_bench.py` は記号と長音だけを無視して比べているので、表記揺れは失敗に数える。
6. **英語区間の頻度コスト。** wordfreq の上位25,000語を単独の英語区間に、上位10,000語（4字以上）＋技術語を編集つきの照合に使っている。短い一般語（mid、shit、bet）がローマ字の一部に割り込む経路が N-best に出る。
7. **`core/types.py` への提案（変えていない）。** 辞書に無い英数字列（`jr`、`cdma`）も `kind="en"` で返しているので、後段からは辞書語と区別できない（区別は `surfaces` が綴りだけか）。`Seg` に「辞書の語か」を示す欄（例: `kind="raw"`）があると、後段がこの区間を英語として扱うか決めやすい。
8. **raw_tokens は本人の用途を模して作った小さなセット（39文）で、英数字列の弧のコストの調整にも使った。** 調整と検証が分かれていない。本人の実際の入力で確かめたい。
9. **体験版の配布物。** `tools/pack-trial.ps1` は `models/reading/kana_lm.pkl` だけを入れる。`kana_lm.pkl` の中身の版が上がったので配布前に作り直しが要り、`models/reading/mozc_readings.marisa` も同梱しないと語のコストを使わずに動く（上位5の選び方の 2 が効かない）。
