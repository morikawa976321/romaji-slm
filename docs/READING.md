# 読みラティス（工程2: 打鍵列 → 読みの N-best）

[REDESIGN.md](REDESIGN.md)「推奨構成」の最初の段。`core/reading.py` の `readings(keys, n=20, max_edits=2)` が、打鍵列から読みの候補（`core/types.py` の `Reading`）をコストの小さい順に返す。英語か日本語かはここで決めず、両方を N-best に残す（決めるのは後段）。

```
uv run python -m core.reading "githubnipushshiteoite"      # N-best とコストの内訳
uv run python -m eval.reading_bench --fails 10             # 合格条件の測定（AJIMEE・user_style_reading）
uv run python -m eval.reading_bench --set wac-test         # コスト調整に使った別セット
uv run pytest tests/test_core_reading.py
```

初回は言語モデルの素材（Mozc 辞書 約60MB、Wikipedia 注釈コーパス 3779 文書）を github から取り、`models/reading/kana_lm.pkl`（約30MB）を作る（30秒〜2分）。`models/` はコミットしない。`uv run python -m core.kana_lm build` で作り直せる。

## 仕組み

打鍵列の各文字位置を節点にし、次の弧を張る。弧は「打鍵列の区間 [start, end) → 読みの断片」で、コストを持つ。

| 弧 | 内容 | コスト |
|---|---|---|
| 正規ローマ字 | `core/romaji_table.py`（Microsoft IME / Google 日本語入力と同じ表。`eval/romaji_kana.py` から移した）。si/shi, ti/chi, tu/tsu, hu/fu, zi/ji, sya/sha, tya/cha/cya, ja/jya/zya、x/l の小書き、fa・thi・dhi・twu・wi・va などの外来音。`nn`→ン、`n`（母音・y・n の前以外）→ン、`n'`→ン、子音の重ね・`tch`→ッ、`-`→ー | 0 |
| nn の揺れ | `nn`+母音・y を「ン+な行」とも読む（`jikkennokekka`→ジッケンノケッカ） | 3.0 |
| ti/di の揺れ | `ti`→ティ、`di`→ディ（user_style に `yu-zabiriti-` の打ち方がある） | 2.0 |
| 編集 | 音節表の各綴り（＋単独の n・nn）に1編集を施した綴り→元の音節。置換は QWERTY 隣接キー（`core/keyboard.py`、`data/noise.py` と共有）、脱字（1字補う）、余計な1字（重ね打ちか隣接キー）、隣接2字の入れ替え。ほかに、促音の子音を落とした形（kite→キッテ）、音節の後ろの i・u・n を落とした形（tasou→タイソウ）、音節をまたぐ入れ替え（ornipikku→オリンピック） | 置換 3.0・脱字 3.5・余計な1字 3.0（重ね打ち 2.5）・入れ替え 3.0 |
| 英語 | 打鍵列の部分文字列が英単語リストに一致する区間（`kind="en"`、`surfaces` は登録表記→綴り）。1編集で一致する区間も（`githib`→github）。英字と `.` `-` 数字の塊（llama.cpp、claude.md、gpt-2、v3.1）も1区間にできる | 下記 |
| 辞書に無い英字列 | 最後の逃げ道（3字まで、と英字の連続の終わりまで） | 5.0 + 1.0/字 |
| 数字 | 数字の連続（中の `.` `,` を含む: 3.14） | 0（英字に挟まれると 1.5、母音・n 以外の英字の直後なら 2.5） |
| 記号 | `,`→(、 ,) `.`→(。 .) `?`→(？ ?) `!`→(！ !) `[`→(「 [) `]`→(」 ]) `/`→(・ /) `:`→(： :) など。数字・英語の塊の中の `.` は持たない | 0 |

制約: 1弧に編集は1つまで（＝1音節・1英単語に1編集まで）、1文で `max_edits` まで。無修正の経路は常に残る（辞書に無い英字列の弧があるので、どんな打鍵列にも編集0の経路がある）。

さらに、かなの弧には**読みらしさ**を足す: カタカナの文字 4-gram（`core/kana_lm.py`）で `0.3 × Σ(min(−log P(字|直前3字), 9) − 3.5)`。英数字・記号の後では文脈を文頭に戻す。

探索: 状態を（位置, 使った編集の数, 直前3字のかな）にして前向きに最良コストを求め、入ってくる遷移を覚えておき、後ろ向きに最良優先で経路を取り出す（前向きの最良コストが正確な残りコストになるので、取り出し順がそのままコスト順）。同じ区間列になる経路は1つにまとめる。各位置で、全体の上位12状態と編集数ごとの上位3状態だけを広げる。

`Reading.breakdown` の内訳: `edit`（編集）、`en`（英語区間の固定分＋頻度）、`en_romaji`、`en_cut`、`nn`、`loan`、`raw`、`num_in_word`、`num_cut`、`sym`、`lm`（読みらしさ。負にもなる）。合計が `Reading.cost`。

## コストの決め方と根拠

### 読みらしさ（文字 4-gram）が要る理由

打鍵ミスの約半分は別の正しいローマ字になる（AJIMEE に `data/noise.py` で1〜2個入れた200件のうち94件は、編集なしでかなに読み切れる。例: `noiraigakuruyouni`→`noiraiakuuyouni`＝ノイライアクウヨウニ）。編集コストだけでは、こうした入力は必ず「編集なしの誤読」が1位になり、正解は1編集の経路の山（1文で数十〜数百本、どれも同じコスト）に埋もれる。最初の実装（読みらしさなし）は打鍵ミス入りの上位5が 24.5%（49/200）だった。

### 言語モデルの素材

- **Mozc dictionary_oss の読み**だけで作った 3-gram: AJIMEE の読みで 1字あたり 3.85 nats。語単位なので、助詞の続き方など語をまたぐ連鎖が無い。打鍵ミス入りの上位5は 48%（96/200）。
- **京都大学 Wikipedia 注釈コーパス**（人手の読み付き、train+dev 34,142 区間・約49万字）を足すと 3.22 nats、Mozc の重みは α=0, 0.3, 1, 3 のうち `data/fixtures/zenz_like.jsonl` で最良の α=3 を採った。
- 次数: 3-gram→4-gram で WAC test の打鍵ミス入り上位5が 143→154/200、1位が 63→92/200。5-gram は試していない（状態が増えて遅くなる）。
- 文コーパスの候補のうち、Tatoeba・Wikipedia ダンプ・青空文庫はこの環境から届かなかった。京都大学ウェブ文書リードコーパス（KWDLC）は届くが、本文の著作権者の許諾を得ていない旨が README にありライセンスの明記が無いので使っていない。

### 重みと編集コスト（調整は AJIMEE ではなく WAC test で）

調整用に、Wikipedia 注釈コーパスの **test**（言語モデルの学習に使っていない）から、かなと句読点だけの 10〜45字の文を200件取り（`eval/reading_bench.py --set wac-test`）、同じ手順で打鍵ミスを入れた。AJIMEE は最後の測定にだけ使った。

格子探索の結果（3-gram、状態数無制限のとき。clean=きれいな入力で1位が正解、misfix=きれいな入力で1位が編集を含む、上位5=打鍵ミス入りで正解が上位5以内。各200件中）:

| 読みらしさの重み | 編集コスト | clean | misfix | 上位5 |
|---|---|---|---|---|
| 0.2 | 3.0 | 200 | 0 | 115 |
| 0.3 | 3.0 | 200 | 0 | 127 |
| 0.4 | 3.0 | 196 | 4 | 128 |
| 0.4 | 4.5 | 200 | 0 | 119 |
| 0.6 | 4.5 | 192 | 4 | 123 |
| 1.0 | 4.5 | 141 | 50 | 116 |

重みを上げると、きれいな入力を読みらしさで「直して」しまい（misfix が増える）、上位5も伸びない。重み 0.3・編集 3.0 が、きれいな入力を崩さない範囲で最良だった。編集コストは置換・余計な1字・入れ替えを同じ値にし、脱字は +0.5（補う字の候補が多い）、重ね打ちは −0.5 にした。

その他の値:
- `lm_base` 3.5: かなの1字あたりの平均的な −log P。これを引くので、英語区間がかなを置き換えても読みらしさの合計が系統的に得も損もしない（引かないと、かなを減らす英語区間が常に得をする）。3.0 と 3.5 で結果はほぼ同じ。
- `lm_cap` 9: これが無いと `lyu`（ュ）・`syi`（シィ）のような珍しいかな1字が、隣接キーの置換（キュ、ショ）に負けた。
- 英語区間: 固定 2.0（技術語 1.5）＋ 0.3×(6.5−zipf)（技術語は 0.3 まで）。綴りがそのままローマ字として読める語（kai、mono、issue）は +1.0（技術語 +0.5）。子音で終わる英語区間の直後に母音・y が来る形（sum|ou、rag|iri）は +2.5。これらが無いと、AJIMEE のきれいな入力で sumou→sum+オウ、uragiri→ウ+rag+イリ のように一般語が割り込んだ（192/200）。
- nn の揺れ 3.0: 1.5 だと読みらしさが「ン+な行」を好み、`kinnitsuna`（キンイツナ）がキンニツナになった。
- 状態数の上限: WAC test で全体の上位 16→12 は上位5 が変わらず、所要は約3割減。全体の上限だけだと、編集を2つ要する正解（user_style の `...dalara,sakinitabetwoite.`）が編集0の仮説に押し出されたので、編集数ごとに3状態を必ず残す。
- 音節の後ろに補う脱字は i・u・n だけ（a・e・o を足しても WAC test の上位5は同じで、弧が増えて遅い）。

## 実測（2026-10-12）

条件: クラウドのコンテナ（Intel Xeon @ 2.10GHz、4 vCPU）、Python 3.13、1プロセス。所要は `readings()` 1回の時間で、言語モデルの読み込みを除く（常駐を想定し、読みらしさのメモは件をまたいで共有）。**ThinkPad（Core Ultra 7 255H）では測っていない。**

| 合格条件（REDESIGN.md 工程2、目安） | 結果 |
|---|---|
| AJIMEE 200件、きれいな入力で1位が正解 100% | **199/200（99.5%）** — 未達（1件、下の失敗例1） |
| AJIMEE に打鍵ミス1〜2個、正解が上位5以内 80% 以上 | **127/200（63.5%）** — 未達。1位 55/200、上位20 150/200 |
| 正常入力の誤補正率 2% 以下 | **AJIMEE 1/200（0.5%）、user_style（typo 以外34文）0/34** |
| user_style_reading 40文 | 1位 35/40、上位5 39/40 |
| うち tech 10文: 英語区間を正しく切り出した経路が上位5以内 | 9/9（英単語を含む9文。era-ga は英語を含まない）。読み全体の一致は 1位 8/10・上位5 10/10 |
| 1件あたりの所要（目安 50ms 以下） | AJIMEE（平均50字）平均 92ms・中央 40ms・p95 367ms。user_style（平均33字）平均 43ms・中央 36ms |

文字数別の所要（AJIMEE、平均／中央）: 0〜19字 25/17ms、20〜39字 59/37ms、40〜59字 90/59ms、60〜79字 208/114ms、100字以上 374/345ms。要件の「20〜30字の文」の範囲では中央値 40ms 前後だが、長い入力では目安を大きく超える。

参考（調整に使ったセット）: WAC test 200件で、きれい 199/200・誤補正 1/200・打鍵ミス入り上位5 154/200（77%）・上位20 175/200。AJIMEE より低いのは、AJIMEE の項目が文の途中で切れた断片（`,hnsakmosono` のように記号や助詞から始まる）を多く含むためと考えている。

user_style の category 別: chat 8/8・8/8、tech 8/10・10/10、academic 8/8・8/8、memo 8/8・8/8、typo 3/6・5/6（1位・上位5）。

### `user_style_reading.jsonl` の付け方

`eval/sets/user_style.jsonl` の40文に、打った文字列どおりの読みを付けた（英語区間は小文字の綴り、かなはカタカナ、記号は全角、`-` は ー）。打ち間違いを含む typo の6文は、意図した読み（元の文と同じ）を正解にした。

- `shashinnookuttekuretearigatou.`（写真送ってくれてありがとう。）は、打ったとおりの「シャシンオオクッテ」を正解にした。`nno` を規則どおり「ンオ」と読むと「オ」が1つ余る（を を o と打った可能性もある）。
- `yu-zabiriti-` はユーザビリティー（ti→ティの揺れ。規則どおりだとユーザビリチー）。

## 失敗例

AJIMEE と user_style から（`eval/reading_bench.py --fails 60` の出力から選んだ）。

| # | 入力（打鍵ミス） | 正解 | 1位 | 原因 |
|---|---|---|---|---|
| 1 | `koboreochitashushihaakinimebae,...`（きれい） | …シュシハアキニメバエ… | …シュシハカイニメバエ…（`ak`→`ka` の入れ替え） | 読みらしさが「ハカイ（破壊）」を強く好み、入れ替え1つ（3.0）を上回った。きれいな入力の唯一の失敗 |
| 2 | `noiraiakuuyouni`（g・r の脱字） | ノイライガクルヨウニ | ノイライアクウヨウニ（順位外） | 脱字2つで別の正しいローマ字になった。正解は編集2つ（7.0）＋読みらしさで、上位20に入らない |
| 3 | `...takaigaisharitsu`（t→g） | タカイタイシャリツ | タカイガイシャリツ（順位外） | 誤りの側も実在する語（外車）。文字 4-gram では区別できない |
| 4 | `shukushotoshitetsuku6tashiro`（t→6） | …ツクッタシロ | …ツク6タシロ（順位外） | 促音の子音が数字に化けた形の編集弧が無い（促音は前後で決まる弧で、編集の索引に入っていない） |

| 6 | `raishuunogetsuyobinihaishanoyoyaku.`（u の脱字） | …ゲツヨウビ… | …ゲツヨビ…（5位） | 同上。ゲツヨビ自体が読みとしてありうる |

| 8 | `ikebyawakarete`（n→b、g→y） | イケンガワカレテ | イケビャワカレテ（順位外） | 置換2つで正しい拗音になった |

失敗の内訳（WAC test の打鍵ミス入りで上位5外の46件を、N=300 で取り直して数えた）: 6〜20位 21件、21〜300位 3件、300位以内に無い 22件。300位以内に無いものは、経路そのものが無い（促音・記号まわりの編集弧が無い、編集が3つ以上要る）か、状態数の上限で途中で落ちたもの。

## 未解決の論点

1. **打鍵ミスの上位5 80% に届かない（AJIMEE 63.5%、WAC test 77%）。** 取りこぼしは「打鍵ミスが別の正しいかなになり、正解が6位以下に沈む」型と「経路が無い・途中で落ちる」型がおよそ半々（上の内訳）。前者は文字 4-gram の読みらしさでは区別しきれない。語の知識（Mozc 辞書の語と接続コスト＝工程3の Viterbi）か zenz の尤度が要る。案: (a) 工程3で、読みの N-best ではなく編集弧つきラティスのまま辞書 Viterbi に渡す、(b) 本工程の N を広げ（上位20で 75%）、後段で絞る。工程3の設計と合わせて決めたい。
2. **きれいな入力の 1位 100% と、打鍵ミスの復元はトレードオフ。** 読みらしさの重みを上げると打鍵ミスの1位は増えるが、正しい入力を直し始める（重み 0.4 で WAC test の誤補正 2%、1.0 で 25%）。いまは「正しい入力を崩さない」側に寄せている（AJIMEE で1件だけ崩れる）。
3. **速度。** 20〜30字なら中央値 40ms 前後だが、60字を超えると 100〜400ms。ほぼすべて Python の遷移ループと読みらしさの計算。ThinkPad 未計測。速くするなら、状態数の上限を下げる（全体の上位 12→6 で WAC test の所要が約3割減、上位5 は 154→151、上位20 は 175→165）か、探索部分を Rust/C に移す。
4. **評価の正解の付け方。** AJIMEE の正解読みは表記の揺れを含む（スラブ／スラヴ）。`eval/reading_bench.py` は記号と長音だけを無視して比べているので、表記揺れは失敗に数える。
5. **英語区間の頻度コスト。** wordfreq の上位25,000語を単独の英語区間に、上位10,000語（4字以上）＋技術語を編集つきの照合に使っている。短い一般語（mid、shit、ide）がローマ字の一部に割り込む経路が N-best の下位に出る。後段で落ちる前提で残しているが、N-best の枠を使う。
6. **`core/types.py` への提案（変えていない）。** 辞書に無い英字列（最後の逃げ道）も `kind="en"` で返しているので、後段からは辞書語と区別できない。`Seg` に「辞書の語か」を示す欄（例: `kind="raw"` を足す、または `surfaces` が綴りだけかで判断する約束）があると、後段がこの区間を英語として扱うか決めやすい。
