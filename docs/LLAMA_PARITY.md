# torch 版と llama-server 版の食い違いの調査（2026-10-18）

変換コアの 2 つの実行方式（torch 版 `core`、llama-server 版 `core-llama`。仕組みは [LLAMA_BACKEND.md](LLAMA_BACKEND.md)）で、
変換結果と速度がなぜ違うのかを、片方だけを変えた変種を作って突き止めた。どちらに寄せるか・どう揃えるかの材料。
**既定の実行方式（torch 版）と常駐入力（ime/）は変えていない。** 変種はすべてオプションで足した。

## 結論

1. **llama 版が正常入力を壊していた 6 件の原因は、GGUF に入った BOS/EOS の ID の取り違えだった。**
   zenz-v3.1-small の `config.json` は `bos_token_id=1`・`eos_token_id=2` と書いているが、トークナイザの実際の値は
   `[PAD]`=1・`<s>`=2・`</s>`=3。`infer.to_gguf`（llama.cpp の `convert_hf_to_gguf.py`）がこの値をそのまま GGUF に入れ、
   llama-server は `<s>` を EOS、`[PAD]` を BOS とみなす。LlamaBackend は「EOS 以外の表層の空なトークン」を禁じるので
   本物の `</s>` を禁じ、文法の終点で `<s>` を選んで止まっていた。現れ方は 2 つ。
   - 候補の変換の点数（lm）に log P(`<s>`) が乗る。同じ候補で torch 版より平均 −26.7、候補ごとに数 nats ぶれる。
     僅差の候補の順位が入れ替わる（「OK→おい」「東京→と京」）。
   - 本物の終わりを選べないので、文法が許す限り字を足して別の経路の終点まで伸ばす（「一新**ン**」「自社制作**久**」「基金**武**」）。
     その候補の自然さが 15 nats ほど落ち、別の読みが勝つ（「一新→一瞬」「自社制作→医者政策」「基金→解禁」）。
     D17 はこれを「文法の行き止まりの刈り込み」のせいと見たが、torch 版に刈り込みを入れても出力はほぼ変わらず、EOS を直すと消える。
2. **EOS を直すと（起動時の `--override-kv`、変換器 `core-llama:eos=3`）6 件のうち 5 件はそのまま消え、残る 1 件（AJIMEE 1414、torch の点差 0.22）も F16 で消える。**
   プロンプトのトークン列は上書きの前後で HF と同じ（BOS は足されない）。
3. **EOS を直したあとに残る差は数値の差だけで、その大きさは量子化で決まる。** F16・`-np 1` は torch 版と出力がほぼ同じ
   （GPU で E セット 896 文中、刈り込みの 1 件と同点の 1 件だけ。刈り込みも torch に合わせる `de=stop` なら前者も消える。CPU では user_style・gen_test 410 文で刈り込みの 1 件だけ）。Q8_0 は同じ候補の自然さの差が中央値 0.13 nats で、
   **CPU では正常入力を 610 文で 4 件壊す**（user_style 86.3% → 82.2%）。`-np 5` は GPU では実行ごとに出力が変わる（Q8_0 で 610 文中 10 件）。
4. 依頼の仮説のうち、**自然さのトークン分割・行き止まりの刈り込み・探索の幅・特殊トークン・語彙に無いバイトは、出力にほとんど効かない**
   （刈り込みは 2400 文で 1 件、探索の幅は 0 件、ほかは 0 件）。
5. **今回わかったもう一つの前提の誤り: これまでの llama 版の速度（D6・D12 の「CPU で torch 版の約 0.55〜0.7 倍」）は GPU の数値だった。**
   手元の llama.cpp の CUDA ビルドは `-ngl` の既定が `auto` で RTX 5060 Ti に載せていた。CUDA を外した本当の CPU では、
   **llama 版（直して速くした版）は torch 版とほぼ同じ時間**（Q8_0 で 0.92 倍、F16 で 0.98 倍、F16・`-np 1` は 2.2 倍）。
6. **torch 版の照合をそのままに forward だけ ONNX Runtime に替えた版（`core-ort`、今回作った）は、全セット 2400 文で torch 版と出力が 1 件も違わず、CPU で 0.72 倍の時間。**
   CPU では一番速い。
7. **torch の既定のスレッド数（論理コア数）は、ほかの負荷があると極端に遅い**（同じ負荷でスレッド 4 の 6 倍）。今の常駐入力はこの既定で動いている。
   スレッド 4 にしても出力は変わらない（E セット 896 文で全件一致）。
8. 推奨: [推奨](#推奨)。**既定は torch 版のまま。速さが要るときは、スレッド数の固定 → ONNX 版の順。llama 版は CPU では選ばない**
   （速さの利点が無く、Q8_0 は精度を落とし、F16・`-np 1` は遅い）。どこまで要るかは ThinkPad の実測で決める。

速度の数値はすべてこのデスクトップ（Core Ultra 5 245KF）で、**別のセッションが 6〜8 コアを使い続けていた負荷下の値**。ThinkPad の判定には使わない。

### 変種

既定の振る舞いは変えず、変換器のオプションで足した（`eval/converters.py`）。

| 名前 | 変換器 | 変えたもの |
|---|---|---|
| T0 | `core` | torch 版の既定 |
| T1 | `core:dp=1` | torch 版に行き止まりの刈り込み（`LatticeMatcher(prune=True)`。llama 版の文法と同じ制約） |
| T2 | `core:mt=0` | torch 版の探索の上限（上位 2000 トークン）を外す |
| T3 | `core:dp=1,mt=0` | T1 と T2 の両方（llama 版と同じ探索） |
| O0 | `core-ort` | torch 版の forward だけ ONNX Runtime に（`core/ort_backend.py`。照合・探索・採点の式は同じ） |
| L0 | `core-llama:np=5,t=8`（Q8_0） | llama 版の従来 |
| L1 | `core-llama:np=5,t=8,eos=3`（Q8_0） | L0 の BOS/EOS を起動時に直す |
| L2 | `core-llama:np=5,t=8,eos=3`（F16） | L1 を F16 に |
| L3 | `core-llama:np=1,t=8,eos=3`（F16） | L2 を `-np 1` に（実行ごとのぶれが無い） |
| L4 | `core-llama:np=1,t=8,eos=3,de=stop`（F16） | L3 の文法で行き止まりを刈らず、入ったら未完にする（torch 版の探索の再現） |
| L7 | `core-llama:np=1,t=8,eos=3,fl=tok,rf=eos,ka=1`（F16） | L3 に速度の変種を入れたもの |
| L1b・L2b | L1・L2 と同じ | 同じ設定をもう 1 回（実行ごとのぶれ） |
| Lz1・Lz1b | `core-llama:np=5,t=4,eos=3,ka=1`（Q8_0、**CPU だけ**） | L1 を CUDA 抜きの llama-server で（2 回） |
| Lz3 | `core-llama:np=1,t=4,eos=3,fl=tok,rf=eos,ka=1`（F16、**CPU だけ**） | L7 を CUDA 抜きの llama-server で |
| Tc4 | `core`（CPU、torch のスレッド 4） | T0 を CPU・スレッド 4 で（スレッド数で出力が変わらないかの確認） |

L0〜L7 の llama 版は GPU で動いていた（上の「調べ方」）。CPU だけで動くのは Lz だけ。

llama 版のオプション: `eos=3`（BOS/EOS の上書き）、`de=stop`（行き止まりで止める文法 `core.gbnf.matcher_grammar_stop`。行き止まりの節点は
DEL の 1 トークンだけを許し、logit_bias −1000 で最後の手段にする）、`fl=tok`（自然さの強制生成を、正規のトークン列の ID の文法 `<[id]>` で行う。
字の途中のバイトだけは文字で書く。b10549 は `<[id]>` で字の途中のバイトを受理すると、その後の EOG で HTTP 500 を返した）、
`rf=fast`（載らなかった logprob を 1 要求のプロンプトの配列にまとめ、上位 64 で探す）、`rf=eos`（下の「速度」）、`ka=1`（HTTP の接続を使い回す）、`ngl=<層数>`。

## 食い違う文の一覧と原因

### 正常入力で llama 版（L0）だけが間違える 6 件

user_style・gen_test・AJIMEE で 6 件。2026-10-15 の 6 件と 5 件が重なる（当時の gen_test 260 は今は食い違わず、代わりに user_style 16 が入った）。
今回足した WAC でも 1 件（174「各般→各班」）あり、原因は同じ EOS。

| セット | id | 正解 | torch（T0） | llama（L0） | torch の 1位と2位の点差 | 原因 |
|---|---|---|---|---|---|---|
| user_style | 16 | OK、それでdeployして。 | ok、それでdeployして。 | おい、それでdeployして。 | 0.20 | EOS（lm のぶれ） |
| user_style | 52 | 東京に行く。 | 東京に行く。 | と京に行く。 | 0.53 | EOS（lm のぶれ） |
| AJIMEE | 1414 | ゴルファーとしても有名で３０も半ばにして突然 | 三十も半ば | 三十の半ば | 0.22 | EOS（lm のぶれ）。EOS を直しても Q8_0・-np 5 では残り、F16・-np 1 で消える |
| AJIMEE | 1615 | タイトルロゴを一新 | 一新 | 一瞬 | 14.31 | EOS（「一新ン」に伸びて自然さが −15） |
| AJIMEE | 1859 | の自社制作 | 自社制作 | 医者政策 | 10.66 | EOS（「自社制作久」に伸びて自然さが −17） |
| gen_test | 215 | は出資金にあたる基金 | 基金 | 解禁 | 16.87 | EOS（「基金武」に伸びて自然さが −16） |

伸びの例（AJIMEE 1615、L0）: 読み「タイトルロゴヲイッシン」の候補は「タイトルロゴを一新ン」になり lm −50.5・自然さ −40.8（torch は「タイトルロゴを一新」lm −0.006・自然さ −25.5）。
「一新」で終点に届いた時点で、文法は「終わる」と「ンを足して別の経路で終わる」の両方を許す。終わりの印が `<s>`（log P ≈ −25）しか無いので、
ンを足すほうが確率が高い。同じ読みの候補で llama 版が torch 版の文の後ろに字を足したものは、gen_test 2496 候補中 42、AJIMEE 1445 候補中 15、user_style 0。

|---|---|---|---|---|---|
| gen_test | 317 | 不二貿易 | 富士貿易 | 不二貿易 | EOS（lm のぶれで当たった。L1 では torch と同じ誤り） |

### 全部の食い違い（T0 と L0、E セット）

`uv run python -m eval.parity_cause`。振り分けは「L1 で消える = EOS」「L1 で残り L3 で消える = 数値（Q8_0・-np 5）」「L3 でも残り、T1 と L3 が同じ = 刈り込み」。
**40 件のうち EOS 28・数値 11・刈り込み 1。** 一覧は [付録 A](#付録-a-t0-と-l0-の食い違い-40-件)。

### EOS を直したあと（L1）に残る食い違い

user_style・gen_test・AJIMEE で 13 件（user_style 1・gen_test 7・AJIMEE 5）。**数値 12・刈り込み 1**。正誤が変わったのは 3 件（AJIMEE 1414 は torch だけ正解、
gen_test 158 と AJIMEE 810 は llama だけ正解）。長い AJIMEE の 2 件（1236・1405、100 字前後）は、確率の低い貪欲生成が途中の僅差で別の道に入ったもの。
F16・-np 1 ではどれも消える。

## 変種ごとの精度

セルは「完全一致／T0 との食い違いの件数・正常入力で T0 だけ正解・変種だけ正解」。句読点 B の 2 セット（打鍵に句読点が無く、正解は句点つき。D31 で句点を
自動で付けないので完全一致は 0%）はゆるい一致（句読点などを除いて一致）で数えた。typo_hard は正解の文が無いので食い違いの件数だけ。
「—」は回していない。L0〜L7 の llama 版は GPU、Lz は CPU だけ。

## 推奨

**既定は torch 版のまま変えない。速さが要るとわかったら、A'（スレッド固定）→ B（ONNX 版）の順に進め、llama 版は CPU では選ばない。**

- 理由 1: 精度の差は実行方式から来ていなかった。llama 版の「精度が低い」は EOS のバグで、直すと数値の差だけが残る。数値の差を残さずに速くできるのは
  B だけで（出力が全件同じ）、CPU では B が一番速い（torch の 0.72 倍、llama 版の C2 は 0.92 倍）。本人の方針「精度が犠牲になるなら速度はやらない」と D16「出力が変わらない高速化だけ」に、B はそのまま合う。
- 理由 2: ThinkPad では未測定。torch 版がスレッド固定だけで 1 秒に収まるなら、依存を増やす B も要らない。
- 理由 3: llama 版の利点（torch を外せる、GPU で速い）は、CPU だけの ThinkPad では速さの面で効かない。CPU の Q8_0 は精度も落とす。Vulkan で内蔵 GPU に載せる（D）なら話は変わるが、未測定。

推奨が覆る条件:

- ThinkPad で B（ONNX 版）でも 20〜30 字が 1 秒を超える → llama 版の C2 か D を検討する。そのときは「同点の入れ替わり」「実行ごとの揺れ」を許すかの本人の判断が要る（下のカード 3）。
- ThinkPad の内蔵 GPU（Vulkan）で llama 版が大きく速く、出力の差も F16 と同程度 → D を第一候補にする。
- 本人が配布物の大きさ（torch の約 250 MB）を重く見る → B か C1 で torch を実行時から外す方向を先にする。
- スレッドを固定すると、どこかの機械で出力が変わる → A' は使えず、B を先にする（ONNX Runtime もスレッド数を決めて同じ確認が要る）。

llama 版を候補に残すなら、方式の選択と無関係に次は直しておく: GGUF の BOS/EOS の ID（`infer.to_gguf` で書き込むか、LlamaBackend が起動時に上書きする）、
`rf=eos`・`fl=tok`・`ka=1` を既定にする、`-np` が 2 以上なら `-c` を 1024×スロット数にする、`-ngl` を明示する（今は CUDA ビルドが黙って GPU に載せる）。

## 本人に要る判断

### カード 1: ThinkPad で速度を測る（作業。下の手順）

これが無いと、どの方式も速度要件（ThinkPad で 20〜30 字 1 秒以内）を満たすかを判定できない。デスクトップの数値は負荷下の参考値で、換算もしない。

### カード 2: 常駐入力の torch のスレッド数を固定してよいか

- 今の常駐入力（ime/）は torch の既定（論理コアの数）で動く。ほかのアプリが CPU を使っていると極端に遅くなる（このデスクトップで、同じ負荷でスレッド 4 の 6 倍、重い負荷では 1 文に数分）。

- 変えるのは ime/ の 1 箇所（起動時に `torch.set_num_threads`）。いくつにするかは ThinkPad の測定（`torch-t4`・`torch-t8` と既定）で決める。
- 選択肢: 「固定する（ThinkPad の測定を見て数を決める）」「今のまま」。

### カード 3（ThinkPad で ONNX 版でも 1 秒を超えたときだけ）: 出力が数件違う速い方式を許すか

- llama 版（EOS を直したもの）は、F16・`-np 1` で 896 文中 1 件（同点）、Q8_0・`-np 5` で 610 文中 13 件、torch 版と出力が違う。Q8_0 は CPU で正常入力を 4 件壊し 0 件直す
  （「写真送って→写真を送って」「OK、それでdeployして→おい、…」）。GPU の `-np 5` は同じ入力でも実行ごとに出力が変わる（2 回で 610 文中 10 件）。
- D16 の「出力が変わらない」は AI が置いた運用で、本人の言葉は「精度が犠牲になるならやらなくていい」。どちらで判定するかを本人が決める。
