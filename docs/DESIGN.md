# 設計

ローマ字（小文字英字・数字・記号）の打鍵列を、ローカルの小型言語モデルで日本語に変換する。

## 要件（2026-10-11 本人確定）

| 項目 | 決定 |
|---|---|
| 入力 | 英語入力モードで打てる文字のうち、大文字英字を除くもの（小文字英字・数字・記号） |
| ローマ字 | 標準ローマ字。打鍵ミス・脱字はモデルが吸収する。母音省略などの略記は扱わない |
| 変換の範囲 | ローマ字→かなも含めてモデルが担う |
| 英単語・記号 | 英語のまま残すか、句読点・長音・全角半角をどうするかはモデルが文脈で決める |
| 記号の打鍵 | できるだけ英字と数字で打ち、記号は最小限（2026-10-12 本人） |
| 変換の契機 | キーを押したときだけ（打鍵ごとのライブ変換はしない） |
| 1回の長さ | 1単語〜1文。ツール側で「推奨する長さの範囲」を設けてよい |
| 出力 | 1候補のみ。誤りが多発したら訂正手段を考える |
| 左文脈 | 速度に余裕があれば渡す。遅くなりすぎるなら渡さない |
| 個人化 | 初版ではしない。誤りが多ければ追加学習を検討する |
| 速度 | ThinkPad P14s Gen 6（Core Ultra 7 255H、内蔵GPUのみ、32GB）で、20〜30字の文を1秒以内 |
| 学習機 | デスクトップ（RTX 5060 Ti 16GB） |
| 用途 | チャット、AIへの指示・技術文、論文・レポート、メモ・日記のすべて |
| 土台 | 既存モデルの流用・微調整でよい |
| 配布 | OSS 公開の可能性あり。公開できるライセンスの素材だけ使う |
| 採用基準 | 明文化しない。実用して体感で決める |
| 作る順序 | 変換コア（ライブラリ＋CLI）を先に作る。IME 化（Windows TSF / fcitx5）は後で決める |

「記号の打鍵」を受けた実装上の扱い（AI の解釈。本人の決定ではない）: 「ん」+母音・y・n は `nn` と打つ前提にし、`n'` は使わない。学習データの半分は句読点を省いた入力にして、モデルが句読点を補う例にする（[DATA.md](DATA.md)）。

ThinkPad は 2028-01 頃まで Windows、その後 Debian 13 に移る予定。コアは OS に依存させない。

## 先行例（2026-10-11 調査）

| 名前 | 入力 | 規模・形式 | ライセンス | 要点 |
|---|---|---|---|---|
| zenz（`Miwa-Keita/zenz-v3.1-small` 等） | カタカナ読み | GPT-2 文字単位。small 90.5M / xsmall 22.5M。GGUF あり（v3.2-small Q5_K_M 73.9MB） | 重み CC BY-SA 4.0（v3.2 GGUF のメタは apache-2.0 と表示、食い違いは未解決） | azooKey の変換モデル。v3 系は `<左文脈><入力><出力>` で左文脈を取る。ローマ字は受けない |
| zenz-v2.5 データセット（`Miwa-Keita/zenz-v2.5-dataset`） | — | 約1.9億ペア（カタカナ読み・出力・左文脈） | 大半 CC BY-SA 4.0、llm-jp-corpus v3 の CC 部分は ODC-BY | 日本語 Wikipedia（2024-02）と llm-jp-corpus v3 由来 |
| romaji2ja（`limoXD/romaji2ja`） | ローマ字直接 | Qwen3 系 約0.3B、fp32 safetensors | 重み CC BY-SA 4.0、コード MIT | 要件にもっとも近い。打鍵ミス対応。正規化後 98.09%（771/786、自作ゲート）、未正規化 約93.4%。英単語・記号の扱いと推論速度の記載なし |
| Karukan（`togatoga/karukan`） | ローマ字→ひらがなは別段（規則） | llama.cpp で GPT-2/Qwen3 系 | MIT OR Apache-2.0 | fcitx5 / macOS の IME。Debian 移行後の組み込み先の参考 |
| AJIMEE-Bench（`ensan-hcl/AJIMEE-Bench`） | カタカナ読み | 200件（左文脈あり100・なし100）JSON | データ CC BY-SA 3.0、コード CC0 | 変換評価の既存ベンチ |

速度の実測値は、255H 上で 100M 級のモデルを動かした公開値が見つからない。ThinkPad で `llama-bench` を回して測る必要がある。参考値として、zenz-v1 は M2 Pro の Mac mini で 1問あたり 0.06 秒（Zenn `azookey/articles/ea15bacf81521e`）。

## 方式の候補

1. **規則でカタカナに変換し、zenz に渡す** — 最速で作れるが、要件を満たさない。英単語はカタカナ化された時点で判別できず、打鍵ミスも規則で落ちる。比較用のベースラインとしてだけ使う。
2. **romaji2ja をそのまま使う** — 要件に最も近い既製品。0.3B で、ThinkPad で1秒に収まるかと、英単語・記号の扱いが未確認。
3. **zenz を、ローマ字を直接受けるように微調整する（本命案）** — 文字単位 GPT-2 なので、ラテン文字を入力側に並べても語彙を拡張せずに済む見込み。90M と 22.5M の2サイズがあり、速度の余裕を左文脈に回せる。学習データは「日本語文 → 読み → ローマ字＋打鍵ミスのノイズ」を規則で生成し、英単語の区間は小文字化した原綴りを入力、元の表記を出力とする。重みは CC BY-SA 4.0 で公開できる。

## 実測（2026-10-11）

### 方式2: romaji2ja の変換精度

`eval/eval_romaji2ja.py`（現在は削除。`python -m eval.run --converter romaji2ja` が同じ手順）。推論は配布元 `code/infer.py` と同じ手順（`{入力}`、貪欲法、fp32）。辞書を引く高速経路（`infer_fast.py` と `lexicon/`）は使わず、モデル単体を測った。

| セット | 入力 | 完全一致 | 記号を無視した一致 | 平均 MinCER |
|---|---|---|---|---|
| AJIMEE-Bench 200件（カタカナ読みを `eval/kana.py` でワープロ式ローマ字に戻したもの） | 配布元の正規化あり | 3.0% | 4.0% | 0.656 |
| 同上 | 打鍵列そのまま | 4.0% | 4.0% | 0.630 |
| 本人の用途を模した40文（`eval/sets/user_style.jsonl`） | 配布元の正規化あり | 0.0% | 7.5% | 0.595 |
| 同上 | 打鍵列そのまま | 5.0% | 5.0% | 0.539 |

出力は入力から離れた文を作る（`ashitanokaigi,nanjikaradakke?` → 「明日はいい天気です」、`githubnipushshiteoite.` → 「犬は庭師が開発しています」）。モデルカードの 98.09% は作者自身のゲートでの値で、汎化性能ではない。

さらに、配布元の正規化（`code/normalization.py`）は空白と記号 `-_'`\/|.,;:!?()[]{}<>"` を入力から捨てる。記号をモデルが文脈で判断するという要件は、この作りでは満たせない。

**方式2は要件を満たさない。**

### ThinkPad（Core Ultra 7 255H）での速度の模擬

`eval/bench_cpu.ps1`（llama.cpp b10549 の `llama-bench`、CPU のみ）。1回の変換を「入力96トークン（文脈なし）または224トークン（左文脈あり）の処理＋32トークンの生成」として所要時間を出した。

模擬の前提: デスクトップの Core Ultra 5 245KF は 255H と同じ Arrow Lake 世代（P コア Lion Cove・E コア Skymont）で、メモリも同じ DDR5-5600。最大クロックは 255H のほうが P で約2%、E で約4%低い。コアマスクで P コアだけ・E コアだけに固定して測った。255H の LPE コア（Skymont 2基・最大 2.5GHz）は、E コア2基の値をクロック比（4.6/2.5 ≒ 1.84）で割り増して見積もった。

計測中、別作業（音声モデルの学習）が P コアに 35〜59% の負荷をかけていた。そのため各条件15回の**最良値**を主に見る。P コアの中央値は最良値の約2倍に揺れた。

| モデル | P4 文脈なし / あり | E4 文脈なし / あり | LPE2 見積もり 文脈なし / あり |
|---|---|---|---|
| zenz-v3.2-xsmall（25.6M, Q5_K_M） | 23 / 40 ms | 37 / 67 ms | 約120 / 240 ms |
| zenz-v3.2-small（95M, Q5_K_M） | 118 / 188 ms | 164 / 299 ms | 約550 / 1050 ms |
| romaji2ja（281M, Q5_K_M） | 407 / 626 ms | 492 / 916 ms | 約1660 / 3220 ms |
| romaji2ja（281M, f16） | 967 / 1230 ms | 691 / 1030 ms | 約2080 / 3320 ms |

読み取れること:

- **100M 級（zenz-small 相当）なら、P/E コアでは左文脈付きでも1秒の数分の1に収まる。** 1秒を超えうるのは、LPE コアだけで動いた場合に左文脈を付けたときだけ。
- **25M 級（xsmall）は、どの条件でも余裕が大きい。**
- **300M 級は、左文脈なし・P/E コアでやっと1秒の半分前後。** 左文脈を付けたり LPE に落ちたりすると超える。
- 内蔵 GPU（Arc 140T）は測っていない。

## 進め方

1. **ベースラインの評価**: 方式2は実測済みで、要件を満たさない（上記）。
2. **速度**: デスクトップ上で 255H を模擬して測った（上記）。100M 級までなら1秒の要件に収まる。
3. **方式3の部品**（クラウドセッションに並行で出せる）:
   - 学習データ生成パイプライン（読み付与・ローマ字化・打鍵ミス注入・英字区間と記号の扱い）— 実装済み。実データで2万件生成（[DATA.md](DATA.md)）
   - 評価の仕組み（文字誤り率・完全一致・AJIMEE-Bench のローマ字版）— ハーネスは実装済み。方式1のベースラインは AJIMEE 87.0%・user_style 57.5%（英単語を含む文 10%・打鍵ミス 17%）（[EVAL.md](EVAL.md)）
   - 微調整スクリプト（CPU で小さい設定が通るところまで。本学習は 5060 Ti）
   - 推論 CLI（GGUF 変換、llama.cpp で `ローマ字 → 日本語`）— 実装済み。llama.cpp は llama-server を子プロセスで使う（[INFER.md](INFER.md)）
4. **本学習と実用試験**（ローカル）

## 確認済みの論点

- zenz-v3.1-small のトークナイザ（GPT2Tokenizer、バイト単位 BPE、語彙 6000）は、ラテン小文字・数字・ASCII 記号をすべて単独トークンとして持つ。**微調整に語彙の拡張は要らない**（2026-10-12、[EVAL.md](EVAL.md)）
- zenz 系のトークナイザは、GGUF の pre-tokenizer を `gpt-2` にすれば公式 llama.cpp で HF と同じトークン列になる。配布 GGUF の `gpt2-small-japanese-char` は azooKey のフォーク独自の名前で、中身は GPT-2 と同じ正規表現（2026-10-12、[INFER.md](INFER.md)）

## 未確認の論点

- zenz の文字単位トークナイザ（ku-nlp/gpt2-small-japanese-char 系）がラテン小文字・記号を単独トークンとして持つか — 調査スクリプトは用意済み（`eval/tokenizer_survey.py`、[EVAL.md](EVAL.md)）。クラウドから Hugging Face に接続できず結論はまだ
- 日本語 Wikipedia 由来の学習で、公開する重みに CC BY-SA が及ぶか（CC 自身は保守的な読みを示しつつ、法的結論は出ていない）。CC BY-SA 4.0 で出す前提なら問題にならない
- 読み付与の精度。学習データは zenz-v2.5-dataset の読みを主に使い、SudachiPy の読みと食い違う英数字なしの文は除外している（2.0%）。両者が同じ誤りをした場合は検出できない
- 学習データの文体の偏り。zenz-v2.5-dataset は Wikipedia・Web の断片が中心で、本人の用途（チャット・AI への指示・英単語混じりの技術文）が少ない
