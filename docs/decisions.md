### D1. 速度の実測は、まずこのデスクトップの CPU で段階別に取る（2026-10-14、AIの判断）

- 事実: Core Ultra 5 245KF（14スレッド）、torch 2.11 CPU fp32、既定 k=5,w=4,f=1 で user_style 14文の中央値 **1151 ms**。内訳は 読み 10〜80ms、k=5 件の制約付き生成が各 180〜400ms（約 13ms/トークン、出力 13〜28 トークン）を逐次、自然さ 40〜60ms。時間の約9割が k 件の逐次生成。
- 決めたこと: 速度の作業は「k 件のバッチ化 → 1ステップの Python 照合の軽量化 → 足切り／k 可変 → 量子化・xsmall」の順。ThinkPad への換算は書かない。
- 覆る条件: バッチ化しても 1 件 1 秒を切らないとき（→ llama-server の GBNF 経路を作る）。

### D2. 作業の順序: 体験版（比較ページ）の経路を現行コアで先に通し、速度・精度・句読点 B は独立に差し替える（2026-10-14）

- **AIの判断**: 採用。比較ページ・サーバ・起動 `.cmd`・配布スクリプトは CPU だけで閉じるのでクラウドセッションに出す（依頼文 [tools/tasks/trial-page.md](../tools/tasks/trial-page.md)、ブランチ `claude/trial-page`）。親は並行してコアの速度（D3）を進め、設定（句読点・英字表記）のインターフェースは依頼文に書いた config の約束に合わせて親が core 側に足す。

### D3. 速度の優先順位: 計測 → k 件のバッチ化 → xsmall → （必要なら）照合の軽量化・量子化。足切りと GBNF は後回し（2026-10-14）

- 事実（マイクロベンチ、Core Ultra 5 245KF、torch 2.11 CPU fp32）: zenz-v3.1-small の KV キャッシュ付き 1 トークンの forward は B=1 で 13.3 ms、B=2 で 14.1、B=5 で 19.0、B=8 で 19.4（14 スレッド）。8 スレッドでは B=1 10.7 / B=5 16.4。xsmall は B=1〜8 で 4.6〜5.8 ms。60 トークンのプロンプト処理は small B=5 で 118 ms。log_softmax+argsort は 0.5 ms/行。ラティス照合（`LatticeMatcher.advance`）は 1 件 5 候補の生成全体で 1〜4 ms。**支配要因はモデル forward のフレームワーク側の固定費**（B を 5 倍にしても 1.4 倍にしかならない）で、Python 照合ではない。
- **astra の意見**: バッチ化を第一候補に。左パディングでは attention_mask に加えて position_ids とキャッシュ更新を正しく扱い、単独実行と出力・EOS・生の対数尤度を比較する。xsmall は早めに比較（「速度優先」の実体になる）。量子化は Conv1D→Linear の同等性確認のあと、十分速ければ省略。足切りは読みコスト差だけでは自然さによる逆転を排除できないので後回し。「デスクトップで p50 400ms / p95 1s 未達なら即 GBNF」という自動分岐には反対で、未達なら移行を比較検討する。固定文法で生成させた logprob が現行の自然さと同じになる保証は無い（再正規化後の確率なら強制トークンが 1 に近づく）ので、llama-server で生の分布から選択トークンの確率を取れるかを先に確かめる。
- **AIの判断**: 採用。順序は (1) バッチ化と逐次実行との同等性テスト、(2) xsmall を制約付きで評価、(3) スレッド数の比較、(4) llama-server の生 logprob の成立性だけ小さく確認、(5) 量子化・照合軽量化は (1)(2) の結果を見て要否を決める。k 可変・足切りは最後。

### D4. バッチ化の結果と、スレッド数は既定のまま（2026-10-15、AIの判断）

- 事実（Core Ultra 5 245KF、CPU、small、k=5,w=4,f=1）: user_style 73文で逐次 中央値 1208 ms / p95 1988 → バッチ 485 ms / p95 775。候補の文と対数確率は 73/73 で一致。20〜45字の24文ではスレッド 4/6/8/10/14 で中央値 424/394/404/362/411 ms（差はばらつきの範囲）。xsmall は同条件で 148〜163 ms。
- 決めたこと: スレッド数は torch の既定のまま（ThinkPad の P/E/LPE 構成では別の最適があるかもしれないが、手元で測れないので配布物の自動計測に任せる）。次は xsmall の精度を制約付きで測り、「速度優先」設定の実体にできるか決める。

### D5. 「速度優先」設定の実体は zenz-v3.1-xsmall（制約付き）にする（2026-10-15、AIの判断）

- 事実（RTX 5060 Ti で精度、CPU で速度。k=5,w=4,f=1）: xsmall は user_style 76.7%（small 82.2%）、tech 60.0%（75.0%）、typo 54.5%（63.6%）、誤補正 9.7%（4.8%）、gen_test 31.5%（34.1%）、AJIMEE 70.0%（84.5%）。CPU（245KF）の 20〜45 字で中央値 約150 ms（small 約400 ms）。
- 決めたこと: 工程4の目安（70/60/50）は満たすが誤補正が2倍なので、既定にはせず「速度優先」として比較ページに並べる。選ぶのは本人の体感。
- 覆る条件: ThinkPad で small が 1 秒を大きく超えるなら xsmall を既定候補に繰り上げる。

### D11. Codex のレビュー（QA 役）で見つかった5件を全部直した。例文の実コア確認（2026-10-15、AIの判断）

- **Codex review の指摘**（verdict: fail、5件 major。いずれも最小の再現条件つきで、親が確かめて正当と判断）: (1) バッチ生成で終了済み系列の position_ids を進め続けると、長いプロンプトの系列が先に終わったとき位置埋め込みの上限を超える。(2) `punct=ja` が全角候補の無い記号（@ + & %）まで除外してラティスが行き止まりになる。(3) `render_en_case` の `str.find` が、先行するかな区間の辞書表層にある ASCII（アイフォン→iPhone の i）を拾う。(4) `bounds` がトークン末尾だけを記録し、複数文字トークン内部の語境界を落とす。(5) `_pick` が `max_tries` より多く走査する。
